# Hamnsignal TUI

## v0.1 Design & Implementation Specification

### 1. Purpose

`hamnsignal-tui` is a terminal client for Hamnsignal.

It connects directly to the public Hamnsignal streams and provides two complementary ways of experiencing the work:

**DATA**  
A restrained information view showing what Hamnsignal is doing right now.

**VISUAL**  
A generative terminal composition driven entirely by live Hamnsignal data.

The client should feel like an alternative interpretation of Hamnsignal rather than a terminal reproduction of the existing browser client.

The visual identity should be sparse, calm, slightly industrial and highly legible.

---

## 2. Core Principle

The two views answer different questions:

> **DATA — What is Hamnsignal doing?**

> **VISUAL — What does Hamnsignal feel like right now?**

The DATA view exposes the incoming state.

The VISUAL view interprets that same state.

No arbitrary animation should exist in the VISUAL view.

**Every visible event must ultimately be caused by Hamnsignal data.**

There should be no decorative screensaver particles, fake randomness or unrelated background animation.

Randomness may be used to vary the representation of a real event, but the event itself must originate from Hamnsignal.

---

## 3. Public Inputs

### Audio

```text
https://hamnsignal.se/live.mp3
```

Audio playback should be delegated to an external player rather than decoded inside the application.

Recommended initial backend:

```text
mpv
```

The TUI starts and controls the player process.

Audio and graphics remain independent. Failure of one must not terminate the other.

### Graphics / State

```text
wss://hamnsignal.se/ws
```

Incoming messages use the Hamnsignal relay event envelope.

The application should primarily depend on:

```text
type
time_unix_ms
fields
```

Unknown event types and unknown fields must be ignored gracefully.

Missing optional fields must never crash the renderer.

---

## 4. Supported Event Types

v0.1 explicitly understands:

```text
voice_start
voice_end
state_update
live_arrival
weather_state
river_state
```

Other event types may be logged in debug mode but otherwise ignored.

---

## 5. Application State

The WebSocket layer should populate a central application state independent of either renderer.

Conceptually:

```go
type AppState struct {
    Connected bool

    Voices map[int64]*Voice

    Semantic map[string]any
    Phrase   map[string]any

    Weather WeatherState
    River   RiverState

    LastArrival *Arrival

    Audio AudioState
}
```

The exact Go structures can evolve during implementation.

The important architectural rule is:

```text
NETWORK
   ↓
STATE
   ↓
 ┌───────────────┐
 │               │
DATA          VISUAL
renderer      renderer
```

Neither view should parse WebSocket packets itself.

---

## 6. Voice State

A `voice_start` creates a visual/music voice identified by:

```text
nodeId
```

Useful properties include:

```text
layer
freq
amp
pan
attack
release
brightness
stability
synth
source
phraseState
phrasePos
motif
```

A `voice_end` marks the corresponding voice as released.

It must **not necessarily disappear immediately**.

Instead, its visual representation should decay according to its release behaviour.

This is particularly important for the VISUAL view.

---

## 7. DATA View

### Goal

The DATA screen should feel more like a monitoring instrument than an administrative dashboard.

It should prioritize:

- whitespace
- alignment
- typography
- hierarchy
- stability

Avoid boxes around everything.

Avoid excessive colour.

Avoid trying to display every available field.

### Approximate Layout

```text
 HAMNSIGNAL                                             LIVE ●

 ───────────────────────────────────────────────────────────────


  GÖTA ÄLV                          MUSICAL STATE

  level       +0.11 m               phrase       REPOSE
  normalized  0.555                 brightness   0.28
                                     voices       4


  WEATHER                           ACTIVE VOICES

  temperature 16.2 °C               CANTUS        329.6 Hz
  wind        4.1 m/s SW            BODY          164.8 Hz
  rain        0.7 mm                BODY          110.0 Hz
                                     SUPPORT         82.4 Hz


  LAST ARRIVAL

  TRAM 3
  MASTHUGGSTORGET · PLATFORM A


 ───────────────────────────────────────────────────────────────

 audio ▶ playing       websocket ● connected
```

This is a conceptual layout rather than a fixed pixel specification.

---

## 8. DATA View Sections

### River

Show:

```text
raw river level
normalized river level
```

Observation age may be added later if useful.

### Weather

Prefer:

```text
temperature
wind speed
wind direction
precipitation
global radiation
```

Only display values currently known.

Missing fields simply disappear.

### Musical State

Show useful semantic/phrase information when available.

Examples:

```text
phrase
brightness
active voice count
```

Additional semantic state may later be promoted after observing the real stream.

### Active Voices

Display approximately 4–8 voices depending on terminal height.

Each should show primarily:

```text
layer/source
frequency
```

Potential secondary fields:

```text
amp
pan
```

Do not expose every synthesizer parameter by default.

### Arrival

Display the latest `live_arrival`.

Example:

```text
TRAM 3
MASTHUGGSTORGET · PLATFORM A
```

After sufficient time without another arrival it may fade visually rather than disappear abruptly.

---

## 9. VISUAL View

### Goal

The VISUAL view is not a graph.

It is not:

- a waveform
- a spectrum analyser
- an oscilloscope
- a scrolling event log
- a terminal copy of the website

It is a generative composition created from the semantic musical and environmental state.

The screen should generally contain **more empty space than occupied space**.

Silence and inactivity should produce visual stillness.

---

## 10. Terminal Drawing Surface

Use Unicode characters where supported.

Primary visual vocabulary:

```text
·
•
─
━
╱
╲

⠁ ⠂ ⠄ ⡀ ⢀
```

Braille characters are particularly interesting because one terminal character represents a 2 × 4 dot matrix.

This allows the renderer to operate on a higher-resolution virtual canvas while still remaining a normal terminal application.

Fallback rendering may eventually support simpler Unicode/ASCII terminals, but that is not required for the first implementation pass.

---

## 11. Voice → Visual Mapping

Each active musical voice becomes a visual entity.

### Frequency

Controls primarily:

```text
vertical position
```

Low frequency:

```text
lower portion of screen
```

High frequency:

```text
upper portion of screen
```

Use a logarithmic mapping rather than linear Hz.

### Pan

Controls:

```text
horizontal position
```

Conceptually:

```text
-1.0 = left
 0.0 = centre
+1.0 = right
```

Do not make this completely rigid.

Small spatial variation is desirable.

### Amplitude

Controls:

```text
visual energy
```

Possible effects:

- mark density
- glyph weight
- line width
- intensity

Very quiet voices should be visually delicate.

### Attack

Controls how a voice enters the visual field.

Short attack:

```text
appears quickly
```

Long attack:

```text
slowly emerges
```

### Release

Controls visual persistence after `voice_end`.

Short release:

```text
quick disappearance
```

Long release:

```text
long residual trace
```

Released voices become visual memory.

### Brightness

Controls symbol character and/or terminal intensity.

Possible progression:

```text
·
⠂
⠒
─
━
```

The implementation should experiment rather than treat this exact sequence as final.

### Stability

Controls spatial stability.

High stability:

```text
steady
coherent
line-like
```

Low stability:

```text
scattered
fragmentary
slightly displaced
```

Movement should remain subtle.

Avoid noisy vibration.

---

## 12. Layer / Source Identity

Different musical layers may develop slightly different visual behaviours.

Initial suggestion:

### body

Longer horizontal or gently curved structures.

### cantus

More isolated and prominent marks.

### cantus_support

Smaller supporting structures surrounding or beneath cantus activity.

### counterpoint

Distinct temporary interruption or answering gesture.

These behaviours should remain related enough that the visual field still feels like one system.

---

## 13. River Mapping

River level acts as a **slow structural influence**, not a notification.

Initial mapping:

```text
normalized river level
        ↓
visual horizon / vertical centre of gravity
```

Higher river values can gradually raise a virtual baseline.

River level may additionally influence:

```text
trace persistence
vertical spacing
overall weight
```

But v0.1 should initially use only one major mapping to avoid over-designing the system.

---

## 14. Weather Mapping

Weather should operate as background pressure on the visual system rather than appear as literal weather icons.

### Wind speed

Influences:

```text
horizontal drift
```

Strong wind creates slightly greater displacement over time.

### Wind direction

Determines:

```text
drift direction
```

### Precipitation

Influences:

```text
fine point density
```

Rain should not literally render falling rain.

Instead it increases the probability of small secondary marks around actual musical structures.

Without musical activity, precipitation should not create a busy autonomous animation.

### Global Radiation

Possible influence:

```text
overall visual contrast
```

This can remain experimental in v0.1.

### Temperature

Do not map initially.

It belongs in DATA view but does not need a visual mapping merely because it exists.

---

## 15. Transit Arrivals

`live_arrival` should produce a clearly perceptible but temporary event.

It should feel different from musical voices.

Initial behaviour:

```text
arrival
   ↓
trace enters one edge
   ↓
crosses part or all of composition
   ↓
fades
```

Possible form:

```text
────────────────────
```

or a narrow moving field of Braille points.

Mode may subtly affect representation:

```text
tram
ferry
```

but this should not become literal vehicle animation.

Do not display route text in the VISUAL view.

The DATA view provides literal information.

The VISUAL view interprets it.

---

## 16. Phrase State

Phrase states such as:

```text
opening
repose
return
```

may influence the global behaviour of the visual field.

However:

**Do not invent mappings before observing enough real events.**

Initially store phrase state and expose it in DATA.

The visual renderer should have a clean extension point for phrase-specific behaviour later.

---

## 17. Time and Motion

Target renderer rate:

```text
20 FPS
```

This is sufficient for slow terminal animation.

Animation should favor:

```text
slow emergence
slow decay
subtle displacement
```

rather than conventional smooth high-frame-rate animation.

The work itself should determine how active the screen feels.

---

## 18. Resize Behaviour

Terminal resize must be supported from the beginning.

The drawing system should use normalized coordinates internally wherever practical:

```text
x = 0.0 … 1.0
y = 0.0 … 1.0
```

Those coordinates are projected onto the current terminal dimensions.

Therefore the composition should work at:

```text
80 × 24
```

and also at:

```text
200 × 60
```

without requiring separate layouts.

The DATA renderer may collapse or hide secondary fields at very small sizes.

---

## 19. Navigation

Keep controls minimal.

```text
TAB      switch DATA / VISUAL
1        DATA
2        VISUAL
SPACE    play / pause audio
?        help
q        quit
CTRL+C   quit
```

The normal interface should not permanently display a large help footer.

Controls may appear briefly after launch and otherwise be available through `?`.

---

## 20. Audio

Audio playback should initially be implemented using `mpv`.

Conceptually:

```bash
mpv --no-video https://hamnsignal.se/live.mp3
```

The application should manage the process.

The UI should know at least:

```text
stopped
starting
playing
paused
error
```

WebSocket reconnects must not restart audio.

Audio errors must not stop visual operation.

Likewise, the graphics client must continue operating when audio is disabled.

---

## 21. WebSocket Behaviour

The client should:

1. connect at startup
2. parse JSON messages
3. update application state
4. reconnect after disconnection
5. tolerate malformed or unfamiliar events

Reconnect should use restrained backoff rather than a tight retry loop.

Example:

```text
1s
2s
5s
10s
10s...
```

On successful reconnection, reset the delay.

Environmental state replayed by Hamnsignal after connection should naturally repopulate current state.

## 24. Command

Normal use:

```bash
hamnsignal
```

Possible v0.1 flags:

```bash
hamnsignal --no-audio
hamnsignal --view=data
hamnsignal --view=visual
```

```bash
hamnsignal --events
```

Avoid building a large CLI configuration surface.

## 25. Colour

The application must work well in monochrome.

ANSI colour should enhance rather than define the composition.

Initial direction:

```text
terminal background
mostly neutral foreground
one restrained accent
muted secondary information
```

Avoid:

- rainbow frequency mapping
- bright spectrum-analyser colours
- neon cyberpunk styling
- excessive coloured status indicators

The terminal's own background should generally be respected rather than painting a fake full-screen background.

---

## 26. Persistence

None in v0.1.

The client represents **now**.

On exit:

```text
state disappears
```

No event database.

No recording.

No historical charts.

No user configuration file.

These can be reconsidered later.

---

## 27. Explicitly Out of Scope

v0.1 does **not** include:

- recording audio
- event recording
- historical graphs
- web interface
- mouse controls
- user themes
- plugin system
- configuration editor
- SuperCollider control
- independent public-data polling
- copying the existing browser visualizer
- waveform display
- spectrum analysis
- terminal image protocols
- Spotify-style metadata
- notifications
- daemon mode

---

## 28. Error Philosophy

Loss of one data source should degrade the experience, not destroy it.

Examples:

```text
no audio
→ visuals continue

WebSocket reconnecting
→ audio continues

river unavailable
→ river influence remains neutral

weather value absent
→ corresponding mapping is disabled

unknown voice field
→ ignore it
```

The interface should avoid filling the screen with technical errors.

Detailed failures may be written to debug logs.

## 30. v0.1 Completion Criteria

v0.1 is complete when:

- `hamnsignal` launches directly into the TUI
- the public WebSocket connects reliably
- reconnection works
- current Hamnsignal state appears in DATA
- active voices appear and disappear correctly
- the stream can play through `mpv`
- TAB switches instantly between DATA and VISUAL
- VISUAL reacts exclusively to real Hamnsignal state
- voice frequency, pan, amplitude and release produce clearly different visual behaviour
- river/weather have subtle global influence
- arrivals create temporary visual gestures
- terminal resizing is reliable
- unknown/missing fields do not crash the application
- macOS and Linux are supported
- quitting cleans up the `mpv` subprocess
- the interface feels intentional at both 80×24 and larger terminal sizes

## 31. Design Test

Before accepting any visual feature, ask:

> **Can we explain which Hamnsignal event or state caused this?**

If the answer is no, remove it.

Before accepting any DATA field, ask:

> **Does knowing this help someone understand what Hamnsignal is doing right now?**

If the answer is no, hide it.

Before adding any feature, ask:

> **Does Hamnsignal TUI become meaningfully better because this exists?**

If the answer is merely “it might be useful someday,” leave it out of v0.1.

## 32. Identity

The desired result is not:

```text
Hamnsignal, but in a terminal
```

It is:

```text
a terminal instrument for observing Hamnsignal
```

The DATA and VISUAL views are two readings of the same live system.

One explains it.

The other lets it leave a trace.

---

### Observed Wire-Protocol Notes

Stage 1 validation against the live Hamnsignal WebSocket established several details that the application must account for:

- Numeric voice fields may arrive as JSON strings rather than JSON numbers.
- `nodeId` may also arrive as a numeric string.
- Decoding must therefore accept both JSON numbers and numeric strings.
- `state_update.value` commonly arrives as a string, including numeric semantic values such as `"0.76"`.
- Environmental observations use `observed_at_unix_ms`.
- `weather_state` and `river_state` are replayed after connection, allowing the DATA view to populate environmental state immediately.
- `state_update` events may repeat frequently, approximately once per second, so rendering should use current state rather than treating every update as a visually significant event.
- `voice_start` and `voice_end` packets may contain additional nested `time`, `type`, and `layer` fields.
- Released voices remain part of the application state so later visual rendering can implement release and decay.
- `live_arrival` is expected to be comparatively sparse and event-driven.

### Implemented v0.1 VISUAL

VISUAL accumulates semantic contributions in one density field before Braille
rasterization: voice envelopes, bodies, cores and valleys; the five-lobe Göta
älv field; arrivals; and bounded precipitation traces. Voice placement is
logarithmic frequency (55–500 Hz) and linear pan. Voice ID selects a stable
muted colour; overlap blends colours; release fades the same topology and hue.

Envelope energy below `0.035` is quadratically attenuated per voice to prevent
weak tails becoming a sheet. Bodies and cores use `×1.7` and `×2.4` scaling so
moderate voices retain local centres. River topology is fixed, turquoise, uses
five lower lobes, level-controlled vertical depth, a 45-second deterministic
drift, wind influence, and the existing subtle voice baseline offset.

Wind shapes the environment. Precipitation retains its local voice-texture
effect and also derives at most eight deterministic, approximately 1.2-second
rain traces from `precipitation / 5` clamped to `[0,1]`. Temperature, global
radiation, and phrase state remain DATA-only. Tram and ferry arrivals are
short and long density disturbances respectively.

Audio is external mpv using `--input-ipc-server`; controls are TAB, 1, 2,
SPACE, ?, q, and Ctrl+C. v0.1 excludes history, persistence, configuration,
and independent data polling.
